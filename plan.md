# Sanskrit Śloka Studio: plan

An interactive app to **generate** slow, clear Sanskrit chant audio and to **learn** from it with word- and syllable-level highlighting.
Status: MVP. Built: backend (FastAPI, Postgres, S3 blob storage via MinIO/AWS/Dokploy, SQLite mirror backup), alignment (MMS_FA), React frontend (Library, Generate, Learn with word/syllable highlight and word meanings + summary, Settings), Colab executors (Drive hand-off and manual bundle; tested with fakes only, not on real Colab). Epics browser (Epics > Ramayana > Kāṇḍa > Sarga > verses, all source variants and meanings, reader text toggle) reads from Postgres tables epic_sargas/epic_verses, loaded by the rerunnable `uv run python -m backend.app.epics_import` from sources/ramayan/unified (26100 verses, 651 sargas; not in the SQLite mirror, re-import to restore). It also serves the Mahābhārata (`--epic mahabharata --src sources/mahabharata/unified`: 18 parvans as kāṇḍa, adhyāya as sarga, southern-only adhyāyas stored at 1000+N, sarga 0 = unplaced supplements; 102670 verses, 2367 sarga rows) and the Harivaṃśa (`--epic harivamsha`: 7408 verses, 125 sarga rows). Mahābhārata CE text is © BORI: internal use only, do not ship without permission. Source pipelines and READMEs: sources/ramayan, sources/mahabharata. Epic audio (Generate > Epic verses): pick scope (verse/sarga/kāṇḍa/whole Ramayana), app materialises critical-text verses into `verses`, auto-suggests meter per verse, creates `awaiting_result` jobs (executor colab_batch) and exports batch.zip; `notebooks/colab_batch.ipynb` (one cell, Drive folder for models/code) renders it and downloads results.zip, which is uploaded back (colab_staged executor then does MP3 + alignment). Results land in the user's Drive under batch_results/ramayana/<kanda>/sarga_NNN/<verse_id>/ (layout is carried in batch.json; batch.zip also carries the worker code, so a stale Drive code copy cannot break a run); `WORKERS` runs N render processes (2 max on a free T4 session: 2 vCPU, 12 GB; speed-up unmeasured); into the app via 'Import from Drive folder' (needs Settings colab_drive_dir mounted locally) or by uploading results.zip. One batch is capped at 2000 jobs. First real Colab run: ~15 s/verse, 3.6 GB RAM and 2.2 GB GPU per worker (COLAB.md). Parallel workers, Drive results and import tested with fakes only. Not built: SSH executor, Claude-drafted meanings pipeline, seeding from the user's verses file. Android/ holds a standalone Capacitor app reusing frontend/ (build flag VITE_STANDALONE; data snapshot from Android/export_data.py: Ramayana Bāla kāṇḍa only, no Mahābhārata; Generate/Settings read-only offline); debug APK builds and is installed on a test phone (110 Bāla sarga-1 chants bundled; epic reader shows a Listen link per chanted verse). Generate has a drop-in 'Align results zip' box (PUT /api/alignment/upload, batch auto-detected). Known: 52 of the 110 sarga-1 chants had alignment rejected (16 vs 17 syllables expected), so they play without word highlights. EC2 Terminal page (/terminal): backend WebSocket /api/ssh/terminal (asyncssh, key file path read on the backend machine, trust-on-first-use host keys in storage/ssh_known_hosts, localhost origin only) relays a PTY to xterm.js; tested against a local fake sshd only, not a real EC2 instance. Quality of audio/alignment is unverified by ear. See README.md to run.
Repo: `backend/` is the implementation; `POC/` holds the earlier experiment scripts and outputs (not needed by the app). Run: `uv run uvicorn backend.app.main:app`; tests: `uv run pytest backend/tests`.

## 4. Data model (SQLite)

- **verses**: id, title, text (Devanagari, lines), source_work, source_reference, source_url, source_edition, notes, origin (`seed`|`user`), created_at. Source fields are required; the UI and seed loader reject a verse without them.
- **meters**: id, display name, wav path, ref_text, syllable_count, sec_per_syll. Filled from `bank.json` at startup.
- **voices**: id, name, checkpoint path, vocoder path, speaker notice, enabled. Seeded with the two bundled checkpoints. Both are the same speaker, so the dropdown is really "checkpoint" today.
- **jobs**: id, verse_id, meter_id, voice_id, executor, device, steps, seed, status (`queued|running|aligning|done|failed|cancelled`), progress (0..1), log, error, timestamps.
- **assets**: job_id, mp3 path, wav path, alignment.json path, duration.
- **settings**: key/value (default executor, device, steps, SSH config, worker URL).

## 5. Generation

**Form**: verse (pick existing or enter new text + required source fields), meter (dropdown + auto-suggest), voice (dropdown), executor (default from Settings, overridable), steps (default 16, overridable), seed.

**Meter suggestion**: count syllables per line with `n_aksharas` and `PT.model_text`, compare to each bank clip's `ref_text` count (the nearest-meter logic in `render_production.py`), and show the reason ("2 × 16 syllables; closest clip: anuṣṭubh, 16"). Optional: run Vāgdhenu's `detect_meter` and show its guess, labelled as a guess.

**Engine** (`engine/synth.py`): refactor `render_cpu.py` into a function `render(verse, meter, voice, steps, seed, progress_cb, device)`:
1. Load DiT + BigVGAN once per worker process (about 15 s, so keep warm between jobs; unload on idle to free RAM).
2. For each pāda: Devanagari → Kannada routing → infer → mel saved → BigVGAN → gate.
3. Stitch with gaps; write WAV; encode MP3 (192k mono, loudnorm) with ffmpeg; write mels for later.
4. Report progress per pāda (parsed from the same `pada{i}` events).

**Progress**: per-pāda only. Finer progress is possible via the diffusion step callback but is not planned.

## 6. Executors

All three share one contract: take a job spec (text, reference clip, voice id, steps, seed) and return the WAV, mels and a log.

| Executor | How | Notes |
|---|---|---|
| **Local** | Subprocess running the engine. `device` = `cpu` or `cuda` (setting). Optional half precision on GPU. | Works today on CPU. CUDA path untested here. |
| **VM over SSH** | rsync job spec (+ reference wav) to the VM, run the engine over ssh in a pre-built env, rsync results back. Config: host, user, key path, remote project dir. | VM needs the repo, weights (~3 GB) and a CUDA torch build installed once. Host key checking stays on. No password auth. |
| **Colab / Kaggle** | A notebook starts the worker service and exposes it through a tunnel; the app POSTs jobs to that URL with a shared token. | **Needs a spike (R2).** Colab's free-tier terms and tunnel rules need checking before I commit to it; I have not verified them. Verse text and the reference clip leave your machine. |

Each executor exposes a `health()` check, shown in Settings with a "Test connection" button. A failed job records which executor ran it.

## 7. Learning view

### Data: `alignment.json` per job
```json
{ "audio_duration": 10.3,
  "lines": [ { "words": [
      { "text": "कर्मण्येव", "start": 0.42, "end": 1.31,
        "syllables": [ {"text": "कर्", "start": 0.42, "end": 0.71}, ... ] } ] } ] }
```

### Alignment pipeline (the hardest part, see R1)
1. Resample generated WAV to 16 kHz.
2. Run an aligner to get word timings.
3. Split each word into syllables with `tts_syllabify` (SLP1) and divide the word's time span among them.
4. Validate: syllable count equals expected (32 for Gītā 2.47), times are monotonic, all within the audio length. A verse that fails validation is marked "alignment unavailable" and the player falls back to line-level timing.

**Chosen: B, torchaudio MMS_FA** (`backend/engine/align.py`): SLP1 → latin letters → CTC forced alignment → per-character times → syllables. Word-level accuracy is unverified by ear. Candidates considered:
- **A.** AI4Bharat IndicConformer (Sanskrit) CTC + `torchaudio.functional.forced_align`. This is what Vāgdhenu's own `training/align_indic_conformer.py` does. Concern: it needs NeMo and a large model, which may not fit this laptop's RAM or the Python/torch pins. Not tested.
- **B.** Another CTC forced aligner. Sanskrit support not verified.
- **C.** No ASR model: use the known syllable count per pāda plus energy/onset detection to place boundaries. Lower accuracy, tiny footprint.

### Player (React)
- Devanagari text rendered per line, per word, per syllable (`<span data-start data-end>`).
- Highlight follows `audio.currentTime` via `requestAnimationFrame`. Current word highlighted; current syllable emphasised within it.
- **Click a word or syllable** → plays only `[start - pad, end + pad]` and stops. A "loop this" toggle repeats it. Slicing is done client-side from the one MP3 (decoded to an `AudioBuffer`), so no per-word files are stored.
- **Speed**: 0.5× to 1.5× slider with presets, using `playbackRate` with `preservesPitch`. Applies to the full play and to word/syllable clicks.
- Controls: play/pause, seek, line repeat, keyboard shortcuts (space, ←/→ word, R repeat).
- **Source card** under the verse: work, reference, edition, link. Always visible.
- Dark theme with a Devanagari-capable web font (Noto Sans Devanagari or similar), sized for reading.

### Library
List of verses with source, available audio versions (voice/meter/steps), and a "Generate audio" button for verses without one.

## 8. Settings page
Default executor, device, steps; SSH config; Colab/Kaggle worker URL and token (stored server-side, never sent to the browser after saving); per-executor test button; disk usage and cleanup of old WAV/mels.

## 9. Risks and open items

- **R1: Word/syllable timing.** The model gives audio only, no timings. Everything in the learning view depends on aligner quality, and I cannot hear the result. Mitigation: validation in §7, spike in Phase 0, and you checking by clicking words.
- **R2 update:** the Colab batch notebook ran for real (Drive hand-off, no tunnel); a stale code copy on Drive caused one failed run. Still open: terms of use for long unattended batches, and VM wipes losing results (not saved to Drive as it goes).
- **R2: Colab/Kaggle executor.** Needs an inbound tunnel from a notebook and compliance with each service's terms. Unverified. May be dropped or replaced by Kaggle only. Will be decided after a spike.
- **R3: Slow playback quality.** You found ffmpeg stretching robotic; browser `playbackRate` uses a similar technique and I have not heard whether it is acceptable. Mel-stretch (`revocode.py`) is the fallback: pre-render 0.85× and 0.7× versions per job and let the player switch. Both left open until you listen.
- **R4: Voice and licence.** The bundled voice belongs to Prof. Prathosh (IISc); the Vāgdhenu README asks users not to impersonate the speaker. The app shows a credit and a "synthetic, not the speaker" notice on the player. Code licences seen: Vāgdhenu Apache-2.0, EdgeSanskrit MIT, IndicF5 MIT, BigVGAN MIT; I have not checked the weights' terms for redistribution beyond what the READMEs state.
- **R5: Pronunciation quality is unverified.** You judged the first attempt robotic and off-meter. This app does not fix that by itself; it depends on which render settings you end up preferring.
- **R6: Memory.** One job at a time. The engine must be unloaded after idle time or the laptop will run out of RAM alongside the browser.
- **R7: Speed.** 3.5 to 7 min per verse locally. The queue and progress UI are required, not optional.

- **R8: Alignment syllable-count mismatch (open).** On Bāla sarga 1, 52 of 110 batch chants were first rejected because the aligner's syllabifier and the text-based counter (`textprep.n_aksharas`) disagree by one (e.g. "16 syllables, expected 17", likely conjuncts such as ज्ञ). Now a count mismatch alone keeps the alignment and flags it (`syllable_count_note` in alignment.json); timing errors still reject. Word timing is trusted, syllable highlights on flagged chants are unverified by ear. `uv run python -m backend.app.realign [ids]` re-aligns finished jobs that have none (~16 s per chant, model reloaded per job: slow, see todo.md).
- **R9: Job worker can hang (open).** On 2026-11-01 four jobs sat at "aligning 0.99" with nobody working them and the worker stopped picking up queued jobs until the backend was restarted. Root cause not found.

Proposals I made without asking (change freely): Vite + TypeScript for the frontend; SQLite via SQLAlchemy; one in-process job worker thread; client-side slicing of audio; alignment run on the machine hosting the backend.
